# 01 - Docker 镜像 CI/CD 方案 - 2026-07-25

## 背景

本项目 fork 自 `Gyyyn/OpenWebTTS`，托管于 `XduDSJ/OpenWebTTS`。原项目支持 Docker 部署（含 `Dockerfile` 与 `compose.yaml`），但无 CI/CD 流水线。本次新增 GitHub Actions 工作流，自动构建 Docker 镜像并发布到 GitHub Container Registry（ghcr.io），便于直接 `docker pull` 使用，无需本地构建。

## 方案设计

| 维度 | 选择 | 说明 |
|------|------|------|
| 触发时机 | push master + 打 v* tag + 手动 | master 推送产出 latest；tag 产出语义化版本 |
| 目标架构 | linux/amd64 | 单架构，构建快（约 10-20 分钟） |
| 镜像仓库 | ghcr.io | GitHub 原生托管，权限用内置 `GITHUB_TOKEN` |
| 镜像名 | `ghcr.io/xdudsj/openwebtts` | owner/镜像名自动小写化 |
| 构建缓存 | GitHub Actions cache (`type=gha`) | 加速后续构建 |

### 镜像标签策略

| 触发 | 产出标签 |
|------|----------|
| push master | `latest`、`sha-xxxxxxx` |
| push v1.2.3 | `1.2.3`、`1.2`、`1`、`sha-xxxxxxx` |

- `latest` 仅在默认分支（master）推送时更新，tag 不覆盖 latest。
- `sha-xxxxxxx` 为 commit 短哈希，便于回溯任意构建。

| 文件 | 类型 | 说明 |
|------|------|------|
| `Dockerfile` | 修改 | 删除 `npm install`/`npm run build`（基础镜像无 Node.js），apt 列表加 `curl`（HEALTHCHECK 依赖） |

| `compose.yaml` | 修改 | 默认拉取 CI 镜像（`image:`），保留 `build:` 注释供本地构建切换；新增 volumes 挂载模型与用户数据 |

| `static/js/pdf.min.mjs`、`pdf.worker.min.mjs`、`marked.umd.js` | 新增（提交） | 前端库构建产物 |

## 前端构建产物方案（关键决策）

### 问题

原 Dockerfile 在 `python:3.11-slim-bookworm` 基础镜像上执行 `npm run build`，但该镜像**不含 Node.js/npm**，CI 中报 `exit code: 127`（command not found）。原项目的 Docker 支持在干净环境里从未真正可用。

### 方案选择

| 方案 | 优点 | 缺点 | 是否采用 |
|------|------|------|----------|
| 多阶段构建（node 阶段构建前端） | git 仓库干净 | Dockerfile 较复杂，每次构建需 npm | 否 |
| **提交构建产物，跳过 npm** | Dockerfile 极简，基础镜像无需 Node，构建快 | git 体积增加，前端改动需本地重建后提交 | **是** |

### 采用理由

本项目前端依赖稳定、改动频率低，提交产物后 Docker 构建完全不需要 Node.js，最简单可靠。

### 产物精简

`static/icons/` 原始 fontawesome 包约 41MB（含 svgs/scss/sprites/metadata 等）。应用仅引用 `icons/css/all.min.css`，它只依赖 `webfonts/`。**仅提交 `css/`（620K）+ `webfonts/`（268K），共 892K**，删去其余约 40MB 运行时不需要的内容。

### 前端改动后的重建流程

修改 `static/css/pre.css` 或前端依赖后，需本地重建并提交：

```bash
npm install
npm run build          # Windows 下 build-pdf-js/build-icons 可能因 `;` 分隔符失败
# 若失败，手动复制：
cp node_modules/pdfjs-dist/build/pdf.min.mjs static/js/
cp node_modules/pdfjs-dist/build/pdf.worker.min.mjs static/js/
rm -rf static/icons && cp -r node_modules/@fortawesome/fontawesome-free static/icons
# 精简 icons（仅保留运行时所需）：
cd static/icons && rm -rf js metadata scss sprites sprites-full svgs svgs-full package.json README.md LICENSE.txt
git add static/ && git commit
```

> 注：`package.json` 中 `build-pdf-js`/`build-icons` 脚本用 `;` 分隔多条 `cp`，在 Windows git-bash 下会解析失败。这是上游遗留问题，Linux/macOS 下正常。

## 使用方法

### 拉取镜像

```bash
# 最新（master）
docker pull ghcr.io/xdudsj/openwebtts:latest

# 指定版本
docker pull ghcr.io/xdudsj/openwebtts:1.2.3
```

### 运行

```bash
docker run -d -p 8000:8000 \
  -v $(pwd)/models:/app/models \
  -v $(pwd)/users:/app/users \
  ghcr.io/xdudsj/openwebtts:latest
```

或使用 `compose.yaml`（已默认拉取 CI 镜像，并挂载 models/users 持久化数据）：

```bash
docker compose up -d
```

> 若需本地构建而非拉取镜像，编辑 `compose.yaml`：注释 `image:` 行，启用 `build: .` 行。

### 手动触发

GitHub 仓库 → Actions → "构建并发布 Docker 镜像" → Run workflow。

## 首次使用前置步骤

1. **镜像可见性**：首次推送后，镜像默认继承仓库可见性。前往 `https://github.com/users/XduDSJ/packages/container/openwebtts/settings` 可调整为 public/private。
2. **无需额外 Token**：工作流使用内置 `GITHUB_TOKEN`，无需手动创建 secret。

## 注意事项

1. **镜像体积优化**：`openai-whisper` 依赖 `torch`，pip 默认从 PyPI 拉带 CUDA 库的版本（约 2-3GB）。Docker 容器默认 CPU 推理（`app.py` 的 `--device` 默认 `cpu`），无需 CUDA。Dockerfile 中先从 PyTorch 官方 CPU 索引预装 `torch`+`torchaudio`（约 200MB），后续 `pip install -r requirements.txt` 发现 torch 已满足版本要求会跳过，不重复拉 CUDA 版。`openai-whisper`/`coqui-tts`/`kokoro` 共用此 CPU torch，功能完整，仅推理速度无 GPU 加速。预计镜像体积减少约 2GB。
2. **构建耗时**：`requirements.txt` 含 `openai-whisper`、`coqui-tts`、`piper-tts` 等，首次构建 15-30 分钟。后续命中缓存会快很多。
3. **GHA 缓存上限 10GB**：本项目依赖层较大，若缓存超限会被淘汰。如遇缓存失效频繁，可改用 `type=registry` 缓存（推到 ghcr.io 专用缓存层）。
4. **数据持久化**：`compose.yaml` 已挂载 `./models` 与 `./users` 到容器，容器重建后模型与用户数据不丢失。`docker run` 方式需手动加 `-v` 参数。
5. **GPU 支持**：当前镜像为 CPU-only。如需 CUDA 加速，需改用 NVIDIA CUDA 基础镜像并从 PyPI 默认索引安装 torch，不在本次范围内。
